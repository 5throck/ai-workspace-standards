# 6.7 Procedure Lifecycle Management

Procedures are structured workflow definitions (`schema.yaml` per procedure)
that describe **who** (`agent_key`), **with what capability** (`skill_key`),
**producing what** (`output_type`), **in what order** (`steps[].id`). They are
the canonical source from which procedure-related skill-graph nodes and edges
are derived.

- **Authoring spec**: `templates/common/docs/procedure-schema-spec.md`
- **Normative design**: `docs/designs/2026-08-29-procedure-schema-design.md`
  (v1.0) and `docs/designs/2026-08-29-procedure-coverage-and-l0-design.md`
  (coverage + L0)
- **Validator**: `bun scripts/validate-procedures.ts --all` (L1–L8, fail-closed)
- **Coverage engine**: `bun scripts/procedure-coverage.ts [--tickets]`

## Locations

| Namespace | Location | procedure_id prefix |
|---|---|---|
| Variant templates | `templates/<variant>/procedures/<name>/schema.yaml` | `co-<variant>-` |
| Workspace root (L0 lifecycle) | `procedures/<name>/schema.yaml` | `l0-` |
| Authoring skeleton | `templates/common/procedures/_template/` | — |

Each namespace owns a closed output-type vocabulary in
`procedures/_output-types.yaml`.

## Normative invariants

1. **Canonical Source Invariant**: procedure YAML is the canonical source;
   procedure-derived skill-graph nodes/edges MUST NOT be manually maintained.
   Repair procedures, never the graph.
2. **outputs / inputs / relations independence**: outputs = produced, inputs =
   consumed, relations = semantic links. Never merge the three.
3. **Steps are canonical graph source**: each step's `agent_key`, `skill_key`,
   `output_type` feed `step_uses_skill`, `step_by_agent`, and `produces` edges.
4. **Single produces-edge rule (INV-4)**: procedure-level `outputs[]` produce
   the procedure→output_type edge; step-level types not in `outputs[]` attach
   to the step's skill. Exactly one produces edge per output type.
5. **Coverage is per `(agent_key, phase)`** and satisfied only by an actual
   procedure step (≥1 step; duplicate coverage is legitimate). Gaps are human
   judgment targets — `PROCEDURE_REQUIRED` or `N/A_JUSTIFIED` — never
   auto-generated.
6. **Procedures are workflow-shaped, not agent-shaped**: one procedure
   connects multiple agents/phases across a natural workflow boundary.
   Per-agent/per-phase decomposition or coverage-driven checklist procedures
   are forbidden.

## Division of labor

Repetitive execution lives in scripts (`create-l3-scaffold.ts`,
`l3-to-variant-pipeline.ts`, `project-to-variant.ts`, `upgrade-project.ts`);
the L0 lifecycle procedures (`l0-create-variant`, `l0-promote-variant`,
`l0-project-to-variant`, `l0-upgrade-project`,
`l0-de-commonization-review`) reference those scripts' skills so the flow is
graph-queryable. Judgment calls route into governance tickets — coverage gaps
register `kind: manual` tickets with a deterministic
`coverage_key: <variant>:<agent_key>:<phase>` (source: `procedure-coverage`),
idempotent on re-runs.

## Sync gating

`/sync` regenerates and verifies the skill graph (including scope graphs);
procedure validation runs via the audit layer. Both must pass before commit.
