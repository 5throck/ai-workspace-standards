# Skill Session Review — Session-Evidence Skill Lifecycle Loop Design

## 1. Overview and Objectives

This design introduces an observation-based skill improvement loop inspired by
Tencent's SkillHone, reinterpreted for this workspace's governance model. The
workspace already has a **static Skill Graph** (ADR-0060, `docs/skill-graph.json`)
that expresses "what is connected to what". This design adds the **dynamic
half**: how real session execution evidence evolves that graph and the skills
it contains.

Core principle:

> **Static Skill Graph + Dynamic Session Evidence + Human Governance**

Every session already records a summary to `memory/YYYY-MM-DD.md` (dev-sync
step 2), and every commit passes through `/sync`. The session log is therefore
already a *persistent decision history* — this design makes it consumable as
evaluation evidence, and wires a review step into the sync pipeline.

### Loop (boundary definition)

```
Detect (automatic) → Accumulate → Triage (human) → Revise (approved)
→ Version bump → Graph / Dependency Revalidation → Next Sessions
```

Evaluation is automatic; revision is human-approved (PM Gateway, AGENTS.md §3).
The system **never** auto-applies skill changes from observations.

### Skill Graph relationship

The loop instantiates the following evidence chain over the static Skill Graph:

```
Session --uses--> Skill --produces--> Outcome --reveals--> Observed Symptom
       --suggests--> Improvement Candidate --approved_by--> Skill Revision
```

The Skill Graph itself (ADR-0060) is NOT extended in stage 1 — review records
live in `memory/skill-review/` and reference skills by name. Graph edge-schema
extension (e.g. a `revealed_by_evidence` edge class) is deferred until the
pilot accumulates enough records to justify schema churn (see §8 Future Work).

## 2. Accessibility

Non-UI work (pipeline scripts + markdown governance docs). WCAG baseline not
applicable; exempt per AGENTS.md §5.1 Row 0 requirement for explicit statement.

## 3. Data Schemas (normative)

### 3.1 Session Evidence — `## Skills Used` in `memory/YYYY-MM-DD.md`

Appended by the agent at session end; template supported by dev-sync step 2.

```markdown
## Skills Used

- skill: market-opportunity-discovery
  usage: primary              # primary | supporting
  outcome: completed          # completed | partial | failed | abandoned
  observations:
    - "Had to manually search financials for each candidate — skill lacks a procedure step"
```

Rules:
- `usage` and `outcome` are REQUIRED per entry; missing fields are WARNed by
  the review script (non-fatal).
- `observations` is a free-text bullet list; each bullet may become an
  Observed Symptom at review time.
- Entries reference only workspace-registered skills (by directory name).

### 3.2 Observed Symptom → Diagnosis → Candidate — `memory/skill-review/YYYY-MM-DD.md`

Generated by `scripts/skill-session-review.ts`. The script generates ONLY the
`observed_symptom` + `evidence` blocks. `diagnosis` and `candidate` are filled
at triage time (human / PM / lifecycle-manager) — separation of observation
from judgment is the load-bearing design decision:

```markdown
## Skill Review Entry — target-company-analysis

```yaml
skill: target-company-analysis
date: 2026-09-06
observed_symptom:
  type: repeated_manual_intervention   # see taxonomy below
  description: "User had to separately search financial data for each candidate company"
evidence:
  sessions: 4
  occurrences: 6
  sessions_list: [2026-09-06, ...]
diagnosis:            # triage-time only; script leaves empty
  likely_cause: ""    # e.g. missing_procedure | stale_description | scope_creep
candidate:            # triage-time only; script leaves empty
  priority: ""        # high | medium | low
  confidence: ""      # high | medium | low
  suggested_action: ""  # revise | add_procedure | update_triggers | deprecate | monitor
  status: proposed    # proposed | triaged | approved | rejected | applied
```
```

Symptom taxonomy (initial minimal set; extended through triage experience):

| type | meaning |
|------|---------|
| `description_trigger_mismatch` | session evidence suggests the skill's description/triggers did not match actual use |
| `missing_procedure` | the skill lacked a step the session had to perform manually |
| `repeated_manual_intervention` | the same manual workaround recurred across sessions |
| `outcome_failure` | the skill was used but the session outcome was `failed` or `abandoned` |

### 3.3 Report metadata

Each `skill-review/YYYY-MM-DD.md` opens with an aggregate header:
`observation_count`, per-symptom-type counts, distinct session count.

## 4. `scripts/skill-session-review.ts` (new)

Responsibilities (all structural; no LLM calls):

1. **Parse** today's `memory/YYYY-MM-DD.md` `## Skills Used` section (§3.1
   schema) and the `git status --porcelain` skill-file changes
   (`skills/*/SKILL.md`, platform copies).
2. **Generate** Observed Symptom + Evidence records per §3.2 (symptom+evidence
   only; diagnosis/candidate left empty). One record per (skill, symptom type)
   pair, deduplicated, with occurrence counts accumulated across sessions.
3. **Structural checks** on skills modified this session:
   - version bumped in SKILL.md frontmatter vs `docs/VERSION_MANIFEST.md`
   - governance record (`docs/lifecycle/skills/<name>.md`) Changelog touched
   - description-vs-triggers consistency warning (description keywords absent
     from triggers)
   - re-run `bun scripts/skill-dependency-analysis.ts --skill <name>` for each
     touched skill
4. **Output**: console report + append/update `memory/skill-review/YYYY-MM-DD.md`.
5. **Schema violations** (missing usage/outcome, unknown symptom type) → WARN,
   never fatal.

CLI: `bun scripts/skill-session-review.ts [--date YYYY-MM-DD] [--json] [--dry-run]`.

## 5. Pipeline Integration (`scripts/dev-sync.ts`)

- **New step 3.96c** (non-fatal): runs `skill-session-review.ts` after the
  existing 3.96a/3.96b validators. Guarded by `existsSync` (L0/L1 scripts are
  core-standardized; scaffolded projects without `memory/` skip gracefully).
- **Step 2 (memory entry template)**: appends an empty `## Skills Used`
  section template to the session summary, with a comment instructing the
  agent to fill it per §3.1. Idempotency check is unchanged.
- **Dependency analysis report**: `skill-dependency-analysis.ts --report` is
  additionally executed as a non-fatal warning step (previously manual-only /
  quarterly). Promoting either to fatal is a separate decision after soak.

## 6. Governance Documentation

- `docs/constitution/06-skill-lifecycle.md`: adds the observation-based
  revision loop procedure (§3 loop diagram), candidate status machine
  (`proposed → triaged → approved/rejected → applied`), and the Changelog
  field guide referencing Observed Symptoms / Evidence.
- `skills/skill-lifecycle-manager/SKILL.md`: adds the **whole-skill revision
  principle** (SkillHone finding): a revision may touch SKILL.md prose,
  `scripts/`, and `references/` together in one approved change — prompt-only
  revisions cannot fix failures living in scripts.
- `skills/sync/SKILL.md`: pipeline step table gains 3.96c; documents the
  `## Skills Used` recording duty.

## 7. Pilot Operation

1. Next 2–3 sessions record `## Skills Used` per §3.1.
2. `/sync` produces the first `memory/skill-review/` reports.
3. First triage cycle: PM/lifecycle-manager fills diagnosis + candidate,
   approves → docs-writer revises → version bump → dependency revalidation
   via the existing 3.96a gate.
4. After soak, decide: fatal promotion of 3.96c checks, taxonomy extension,
   and whether skill-review records should surface in the Skill Graph.

## 8. Future Work (explicitly out of scope for stage 1)

- LLM-driven behavioral probes / regression evals (SkillHone's eval harness) —
  revisit once `Skills Used` statistics accumulate.
- Skill Graph edge-schema extension for evidence links.
- Fatal promotion of the review gate.

## 9. Trade-offs

- Single PR: dev-sync mutates shared pipeline files every commit; multiple PRs
  would conflict (CONSTITUTION.md §3.3).
- Non-fatal start: false positives must not block /sync; escalation is a
  deliberate post-soak decision (ADR-0055 WARN-first playbook).
- Observation source is session self-report (agent-authored), not instrumented
  execution — lower fidelity than SkillHone probes, but zero marginal cost and
  already governance-native.
