### W4 — codex-settings policy unification (upgrade-policy three-way split)

`scripts/lib/upgrade-policy.ts` v1.15.0 (`resolveClaim`, the claim SSOT) classifies the three platform config files differently:

| File | Current claim | Mechanism | Effect on upgrade |
|---|---|---|---|
| `.claude/settings.json`, `.gemini/settings.json` | JSON_MERGE / TEMPLATE TREE SYNC | `JSON_MERGE_FILES` (line 137) → merge at `upgrade-project.ts:2334` | deep merge; project-only keys preserved and logged |
| `.agents/mcp.json` | **SYNC** / TEMPLATE TREE SYNC (blanket `.agents` branch, line 328) | falls through — not in `JSON_MERGE_FILES` | project edits destroyed on upgrade |
| `.codex/config.toml` | ADD_IF_MISSING / TEMPLATE TREE SYNC (`.codex` blanket branch, line 325) | seeded only when absent | template updates never reach existing projects (drift by design) |

**Fleet evidence (2026-09-25):**
- `.agents/mcp.json` exists only in `templates/common/` (no variant copies). Sampled project copies (co-abap, co-newbiz, co-safety, co-game) are **byte-identical** to the template seed today — a JSON_MERGE switch is a no-op rollout, and it protects the future customization the blanket SYNC would destroy. The file is pure JSON of the same shape as root `.mcp.json`, which joined JSON_MERGE in upgrade-policy v1.2.0 (ADR-0076) for exactly this reason.
- `.codex/config.toml` project copies are **genuinely customized** (co-abap: `[features] codex_hooks = true` plus additions; co-consult: diverged ADR references and content). ADD_IF_MISSING is load-bearing. No TOML parser exists in `package.json`; a comment-preserving semantic TOML merge is new delivery machinery — outside this batch's non-goals.
- `tests/unit/check-drift-classification.test.ts` pins `classifySettingsDrift` (propagate-to-templates.ts:772) — an **L1→L2** `.gemini/settings.json` classifier. `propagate-to-templates.ts` has no `.agents/mcp.json` / `.codex/config.toml` domain, and no variant carries `.agents/mcp.json`, so **no L1→L2 pair exists for the file** — that test file is not the extension surface (premise corrected with evidence; see D8). The real pins live in `tests/unit/upgrade-policy.test.ts` (JSON_MERGE test at lines 245-247; ADD_IF_MISSING pin for `.codex/config.toml` at line 104) and the `tests/unit/upgrade-tree-sync.test.ts` integration fixture pattern (codex-merge-claim-routing design D5: `mkdtempSync` + `git init` + spawn the real script with `--dry-run`/apply, assert verdicts and bytes; pre/post dry-run diff with an allowlist of permitted differences).

Root cause: registry rows are updated by hand while SKILL.md frontmatter moves with every feature commit, and nothing reconciles one with the other. The scaffold reconcile (`new-project.ts` §6.4) fixes project copies but not the template/root sources, and its "UPDATED" log lines were observed confusing operators (a scaffold run reports drift the operator never authored).

**W5 adds the missing mechanism, not just the fix:** a sync script that converges all four registry surfaces from frontmatter, wired as a dev-sync step so every `/sync` re-converges them, plus a VA-08 validator so non-dev-sync paths still catch drift.

## 2. Goals

1. G1 (W1): the 7 remaining variants carry parseable, frontmatter-sourced registry rows for 100% of their skill dirs (125 rows; rows == dirs per variant), with co-safety's inherited/exclusive split marked in the notes cell.
2. G2 (W2): the 13 "Variant agent sections" WARNs drop to 0 by validating the **resolved** stub body end-to-end, and the resolved body actually satisfies the check (common-body content gap closed).
3. G3 (W3): a machine check (VA-07) compares SKILL.md frontmatter versions across each variant's platform mirrors and against authored registry rows; it runs green today and soaks as WARN with a dated promotion ticket.
4. G4 (W4): `.agents/mcp.json` upgrades by deep merge (project customizations preserved); `.codex/config.toml` keeps ADD_IF_MISSING with a documented rationale; dry-run matrix evidence proves preservation.
5. G5: declaration/validation/policy truth only. No delivery-behavior change except the W2 common-agent section addition (flagged).
6. G6 (W5): all four skill registry surfaces (root workspace rows, root Variant-Exclusive catalog, common scaffold seed, 13 curated variant registries) are machine-converged with SKILL.md frontmatter on every `/sync`, and a validator (VA-08, WARN soak) catches drift on every other path.

## 3. Non-goals

1. Claude Desktop App surface (documented consumer — verifier-expansion design §17.2).
2. New platform surfaces (no fifth mirror tree).
3. Delivery-machinery changes beyond the W4 claim/policy edits — specifically **no TOML merge engine**.
4. `Projects/**` content.
5. Backfilling `last_reviewed` on the 53 co-safety skills (rows record `—`; content churn without information gain).
6. Extending `classifySettingsDrift` to files with no L1→L2 pair (see D8).
7. A config.toml drift detector (candidate follow-up; the divergence class is documented, not detected).

## 6. Design decisions and trade-offs

### D1 — W1 notes convention: three explicit classes in the notes cell

| Option | Pro | Con | Decision |
|---|---|---|---|
| (a) Three-class notes markers (exclusive / fork / plain copy) | The ticket demands the split; the test can pin it; future plain copies self-identify | Slightly richer schema than PR D | **Chosen** |
| (b) Two sections in co-safety's file (Registry + Inherited) | Visual separation | Breaks single-table parseability; `parseSkillRegistryRows` is section-agnostic (scans all rows under any content), so two tables add no machine value | Rejected |
| (c) Keep PR D's single `<variant> only` note for all 60 | Uniform | Falsifies provenance — 8 rows are not co-safety-only; the ticket explicitly requires the split | Rejected |

The parseable row shape is unchanged; classification rides the free-text notes cell, exactly where PR D put per-skill purpose. The W1 test asserts the fork marker set by name, so reclassification drift fails CI.

### D2 — W1 header: curated header for all seven, including co-price

Six variants start `# Skills Index` and are silently regenerated on every verify-skills pass — their current tables are not durable state, so replacing them loses nothing. co-price's `# Agent Skills Guide v4.1` is not regenerated but is stale prose referencing root-level operator skills; a curated registry is strictly more accurate. All seven adopt the co-consult header (`# SKILLS.md — Skill Lifecycle Registry`), which both opts out of the legacy regeneration path and matches the PR D test convention. Usage prose survives where it exists and is accurate (co-news, co-safety, co-work incl. its promotion note); the standard two-sentence Usage note is authored where absent (co-abap, co-export, co-hr, co-price).

### D3 — W2 resolve-and-check (not skip), with a pure compose function

| Option | Pro | Con | Decision |
|---|---|---|---|
| (a) Resolve-and-check via a read-only compose helper | Validates the stub pattern end-to-end; a broken common body still gets caught; PR D QA advisory O1 as written | New pure helper + resolver refactor | **Chosen** |
| (b) Skip `extends:` stubs in the check | One-line change | The stub pattern becomes invisible to the section gate; a future common-body regression ships silently — exactly the failure the advisory warns about | Rejected |
| (c) Reuse `resolveAgentExtendsStub` directly in audit.ts | No new helper | It **writes in place** — a validator must not mutate the template tree it audits | Rejected |

Single fix site: audit.ts. qa-gate.ts has no copy (it shells audit.ts at Step 1 — verified), and validate-templates Check 4 already resolves extends and passes. The section list comes from `golden-reference-loader.ts` `AGENT_LAYER1_SECTIONS` (byte-identical today), making the golden reference the SSOT instead of a second inline list.

### D4 — W2 close the content gap: author `## Output Format` into the common i18n-specialist body

Resolve-and-check alone leaves the 13 WARNs alive against the resolved body — the common body lacks `## Output Format` (verified). The section is part of the canonical specialist structure every variant full-copy agent already carries; the common body is the outlier. Authoring one short section fixes the actual defect, delivers a complete agent to future projects (flagged as the batch's one delivered-content change), and lets the check stay strict. Coordinated version bump (frontmatter + contract entry 1.0.0 → 1.1.0, contract top version → 1.8.0) keeps C-CM-03a green and semver honesty. The 13 stubs keep `version: "1.0.0"` — the stub version describes the stub file; no check binds the two (verified).

### D5 — W3 check identity and semantics: VA-07, mirror-set-based, WARN-soaked with its own promotion ticket

VA-04/05/06 are taken; §17.1's "VA-04-style" phrasing is about placement (validate-templates, VA-03 family), not the literal ID. Comparison semantics:

- **Source of truth**: SKILL.md frontmatter `version:` in each mirror (the same field Check F compares at ROOT; `extractFrontmatterVersion` reused).
- **Primary rule**: mirror-to-mirror equality per skill (present in ≥2 mirrors).
- **Secondary rule**: mirror vs authored registry row (only when a row exists — adapted copies without rows are out of scope by construction).
- **Exemption**: `mirror-parity: skip` (VA-03's vocabulary — one exemption language for the file class).
- **Missing version**: a finding (fail-closed per finding), still WARN-soaked.

A dedicated promotion ticket (not an edit to T-20260925-002) keeps that ticket's enumerated scope stable; the same `not_before: 2026-10-09` date aligns both promotions into one review window. Legitimate divergence was investigated and none exists (fleet scan: 0 mismatches; WS-05a copies share versions; fork rows mirror fork frontmatter), so day-one WARN count is 0 — the soak guards regrowth, exactly the Finding-C prevention §17.1 asks for.

### D6 — W4 `.agents/mcp.json` → JSON_MERGE

Same genus as root `.mcp.json` (ADR-0076 v1.2.0 joined it for the identical reason: projects may register project-only MCP servers). Pure JSON, merge machinery already exists (`upgrade-project.ts:2334` via `mergeSettingsJson`), branch order already routes `JSON_MERGE_FILES` above the `.agents` blanket (lines 303 vs 328 — verified). Fleet copies are byte-identical today, so the rollout is a no-op for existing projects and protective for future ones. The blanket-SYNC destruction risk is real: any project adding an MCP server would lose it on the next upgrade.

### D7 — W4 `.codex/config.toml` stays ADD_IF_MISSING, documented

| Option | Pro | Con | Decision |
|---|---|---|---|
| (a) ADD_IF_MISSING + rationale comment | Zero machinery; protects real fleet customizations (verified: co-abap `codex_hooks`, co-consult divergence); ADR-0076 D4 ruling stands | Template config updates never reach existing projects | **Chosen** |
| (b) TOML-aware merge | Closes the drift gap | New parser dependency + comment/structure-preserving merge machinery = new delivery machinery (non-goal); high blast radius for a rarely-changing file | Rejected |
| (c) Blanket SYNC like mcp.json today | Uniform | Would destroy verified project customizations on every upgrade | Rejected |

The accepted trade-off (template-side config.toml changes reach only new projects) is now written down at the claim site instead of living as tribal knowledge. A cheap drift *detector* (WARN listing divergences) is a candidate follow-up, deliberately out of scope.

### D8 — `check-drift-classification.test.ts` is not extended (premise corrected)

The task brief expected to extend the `classifySettingsDrift` pins for the new policies. Evidence says no: `classifySettingsDrift` classifies **L1→L2** `.gemini/settings.json` pairs; `propagate-to-templates.ts` has no mcp.json/config.toml domain; no variant template carries `.agents/mcp.json` (only `templates/common/` does), so no L1→L2 pair exists to classify. The real pin surfaces for W4 are `tests/unit/upgrade-policy.test.ts` (claim classification) and `tests/unit/upgrade-tree-sync.test.ts` (merge behavior). Extending the drift classifier would add dead code for a file class that does not exist in the L2 trees.

### D9 — Packaging: one PR, ordered W1 → W2 → W3 → W4

All four items are small, declaration/validation/policy-level changes; the codex-merge batch (T-010/T-011) shipped comparably scoped upgrade-behavior changes in one PR with fixture evidence. W4 is the only item touching upgrade behavior, and its risk is bounded by the byte-identical fleet state and the D5-style matrix — the PR description carries that evidence, which satisfies the PM's single-PR intent without a split. Order matters once: W1 precedes W3 (VA-07's registry cross-check reads the new rows). W2 is independent; W4 is independent.

### D10 — W5 sync placement: /sync pipeline step, not a hook; validation as WARN-soaked VA-08

| Option | Pro | Con | Decision |
|---|---|---|---|
| (a) dev-sync Step 4.63 apply-mode sync | Converges in the same commit that bumps frontmatter; one code path; idempotent so extra runs are free | Registry drift from manual edits persists until the next /sync | **Chosen** |
| (b) PostToolUse hook on every SKILL.md write | Zero-lag convergence | Fires mid-edit on multi-file changes (partial state); hook latency on every skill touch; /sync remains the commit gate anyway | Rejected |
| (c) Manual discipline (status quo) | No machinery | This is exactly how the 17-row seed drift, the catalog ghost row, and the co-design row accumulated | Rejected |

Validation is layered: unit tests give fast CI feedback (extended to common seed, root sections, co-design/co-game — the three surfaces whose drift survived precisely because no test read them), VA-08 in validate-templates covers every other execution path and soaks as WARN per ADR-0055 with the T-20260925-007 promotion ticket (same 2026-10-09 window as VA-07's T-20260925-006, so both severity flips land in one review). The catalog section gets a dedicated reconcile because its 7th column is `variant`, not `notes` — running the generic notes-preserving reconcile over it would misread the column. Multi-variant skills (code-review/refactoring/test-driven-development live in co-develop and co-game today) list all owner variants in the cell; divergent frontmatter across owners is reported, never auto-resolved.
