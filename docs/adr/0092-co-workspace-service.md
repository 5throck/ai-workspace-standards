# ADR-0092: Team Gateway — a Docker Web Service Serving Variant Agent Teams over OpenAI- and Anthropic-Compatible APIs

## Context

The 14 variant team templates (`templates/co-*`) are CLI-harness workspaces: their multi-agent teams (PM gateway, specialists, skills) run only inside Claude Code / Gemini CLI / Codex / Hermes sessions. Web clients — including Open WebUI, the originally requested integration target, and Anthropic Messages-API clients — cannot reach them, because the teams expose no HTTP surface. Follow-up analysis (2026-09-27 session) verified the building blocks for a generic bridge: (1) `scripts/new-project.ts` scaffolds a variant project unattended with `--variant --platform hermes --yes`; (2) Hermes Agent provides a machine-readable headless session protocol (`hermes chat --format stream-json`), per-container config isolation (`HERMES_HOME`), project-skill trust (`skills.trusted_project_dirs`), and run ceilings; (3) template releases are versioned artifacts (ADR-0089). The user requested a Docker-based web service that, on request, creates a project from `templates/<variant>` and serves user sessions against it, with environment-variable configuration and no user-facing configuration burden.

## Decision

> **Superseded naming and posture (see Addendum 5 and Addenda 6-10).** This section is preserved as the original 2026-09-27 record. The service was rebranded: current names are `services/co-workspace/` and `CO_WORKSPACE_*` env vars (no code reads `TEAM_GATEWAY_*`; e.g. `TEAM_GATEWAY_RUNTIME` is now `CO_WORKSPACE_RUNTIME`, `TEAM_GATEWAY_LOGIN_REQUIRED` is `CO_WORKSPACE_LOGIN_REQUIRED`). The Phase 0 posture in Decisions 1, 3, 6, 7 and 8 below (no auth, loopback, single container) no longer describes the deployed service.

1. **New L0 platform component `services/team-gateway/`** *(superseded: now `services/co-workspace/`, Addendum 5)*: a single bun HTTP server (zero new npm dependencies) with its own `AGENTS.md`, living under the top-level `services` directory (allowlisted in `docs/workspace-schema.json` `rootAllowlist.dirs`; per-service names are not listed), and never shipped to scaffolded projects. The service consumes `templates/` read-only; no template, agent, skill, or script content changes.
2. **Tenant provisioning = existing scaffold pipeline, via subprocess**: `bun scripts/new-project.ts <tenant> --variant <co-*> --platform hermes --yes` inside the workspace clone, then relocation of the finished self-contained project to `<DATA_DIR>/tenants/<id>/project`. The subprocess boundary is deliberate — `new-project.ts` has no import API and rejects destinations outside the workspace clone.
3. **Session runtime = headless Hermes per tenant**: `hermes chat --format stream-json --in <tenant project> --continue gw-<tenantId> --create-if-missing --accept-hooks --max-turns <N> --run-budget <seconds>` with a per-tenant `HERMES_HOME` (one SQLite `state.db` per tenant; never shared). *(Runtime selection is now `CO_WORKSPACE_RUNTIME` — hermes, antigravity, claude, or codex — Addenda 3 and 5.)* Continuity uses deterministic named threads — live verification found `--resume latest` restricted to the CLI source family (`run_agent.CLI_FAMILY_SOURCES`), and `--usage-file` restricted to the top-level `-z` mode, so token accounting reads the terminal `result` envelope instead. `chat --format stream-json` is chosen over `-z` because `-z` is plain-text only, hides the session id, and auto-bypasses approvals.
4. **Skill trust carries the ADR-0088 D7 posture into the service**: each tenant `HERMES_HOME`'s generated `config.yaml` sets `skills.project_discovery: true` and `skills.trusted_project_dirs` scoped to that tenant's project directory only — the prompt-injection defense stays per-tenant, never blanket.
5. **Wire surfaces are OpenAI- and Anthropic-compatible**: variants are exposed as models (`GET /v1/models`), chat speaks `/v1/chat/completions` (SSE streaming translated from Hermes JSONL) and `/v1/messages` (Anthropic Messages wire, including a `count_tokens` estimate stub), so Open WebUI, Anthropic SDK clients, or any OpenAI-wire client attaches without custom code. A native REST surface (`/sessions`, `/tenants`, `/tenants/:id/chat`) coexists for programmatic control, plus a single-file demo page as a dev aid.
6. **Three-tier configuration**: infrastructure via `TEAM_GATEWAY_*` env vars *(superseded: `CO_WORKSPACE_*`)* (including `TEAM_GATEWAY_HERMES_MODEL`, stamped into each tenant `config.yaml` as `model.default` — without it tenant homes resolve to the paid default model); tenant parameters injected at scaffold time; secrets copied from an operator-designated seed home into each tenant `HERMES_HOME` at provision time and never returned by any endpoint or log line. *(Superseded in part: `auth.json` is no longer copied per tenant (Addendum 4); static provider keys replace the copy-based OAuth mechanism (Addendum 8), with the accepted plaintext-stamp risk of Addendum 9 and the corrections of Addendum 10.)*
7. **Phase 0 posture is labeled honestly**: loopback bind by default, no authentication, single container, per-tenant `HERMES_HOME` as the only isolation boundary. Authentication, per-tenant containers, egress policy, and quota enforcement are explicit Phase 2 items (design doc §10); the runbook states that Phase 0 is local-only. *(Superseded: Addendum 2 added bearer-key auth, quotas, and docker isolation; Addendum 5 added multi-user accounts and the login gate (`CO_WORKSPACE_LOGIN_REQUIRED`, default true in compose); Addendum 6 added the CSRF guard, per-user tenant identity and admin tooling. Loopback bind remains the default for bare-metal runs.)*
8. **Template pinning follows the release cadence, currently degraded**: `TEAM_GATEWAY_TEMPLATE_VERSION` maps to `--version` (tag `template-vX.Y.Z`), but the pinned path is defective on main (`git archive <tag> --list` misuse — T-20260927-019), so Phase 0 treats the pin as unavailable and scaffolds unpinned until upstream fixes it (ADR-0089 cadence still governs image rebuilds). *(Superseded: the pin is now `CO_WORKSPACE_TEMPLATE_VERSION` and works again — Addendum 3 fixed T-20260927-019.)*

## Consequences

- **Positive**: one runtime serves every current and future variant (L0→L2 uniformity is the asset); Open WebUI integration for co-consult and siblings is answered by the wire format rather than per-project shims, and Anthropic SDK clients attach through the same tenants; live-verified end to end on 2026-09-27 (provision → scaffold → relocate → seed → multi-turn named-thread chat with continuity → OpenAI completion and Anthropic message envelopes with mapped token usage); token accounting groundwork enables later quota/billing; provisioning reuses the E2E-tested scaffold pipeline instead of new logic.
- **Cost**: a new L0 surface to maintain (server, Docker, demo page) outside `scripts/` tooling conventions (own tsconfig; no SCRIPTS.md row by design); a coupling to Hermes' stream-JSON protocol — mitigated by pinning the Hermes version per deployment and a defensive parser (unknown events pass through raw); per-tenant scaffold latency (observed ~10–20 s live) handled by async provisioning.
- **Neutral**: templates and governance rules are untouched; ADR-0078 is not implicated — tenant sessions operate inside their own tenant project instance, while repository-landing work continues to route through the workspace PM Gateway; `.hermes/skills` delivery via the existing sync pipeline is unchanged.

## Addendum 1 (2026-09-27): Gemini Wire Surface

Live multi-surface use surfaced demand for Google-ecosystem clients. Antigravity (the IDE/CLI behind the `.agents/` platform mirror) exposes no public model-serving API spec — its extension surface is MCP — so the ecosystem-standard Gemini contract is served instead: `POST /v1beta/models/{model}:generateContent`, `:streamGenerateContent?alt=sse` (per-delta candidate chunks, terminal `finishReason: STOP` + `usageMetadata`), `:countTokens` (chars/4 estimate stub), and `GET /v1beta/models`. This amends Decision 5's surface enumeration ("OpenAI- and Anthropic-compatible" → also Gemini-compatible); all other decisions are unchanged. On this wire `systemInstruction` is ignored (tenant teams define their own instructions from AGENTS.md), and tenant keying uses the optional gateway-extension `user` field, defaulting to `default`.

## Addendum 2 (2026-09-27): Phase 2 Hardening Landed

The §10 roadmap items enforceable by the gateway process are implemented (design `docs/designs/2026-09-27-co-workspace-phase2-hardening-design.md`): optional bearer-key authentication on every non-exempt route (`TEAM_GATEWAY_API_KEYS`, now `CO_WORKSPACE_API_KEYS`; constant-time compare; Phase 0 localhost mode preserved when unset), per-tenant lifetime quotas enforced pre-turn (`TEAM_GATEWAY_TENANT_MAX_TURNS`/`_MAX_TOKENS` → `429`; token counters from the result envelope), first-class toolset scoping (`TEAM_GATEWAY_HERMES_TOOLSETS` → `-t`), and an opt-in per-tenant container isolation mode (`TEAM_GATEWAY_ISOLATION=docker` — per-turn ephemeral sibling container mounting only the tenant project dir and Hermes home; startup fails fast when Docker is unusable; live-verified with a container-side session). Network egress enforcement remains host-side by design (Hermes iron-proxy, operator-deployed) — the gateway contributes toolset scoping and run ceilings, not invented config keys. This addendum records N1/N2/N5 of the Phase 0 design as superseded for this scope.

## Addendum 3 (2026-09-27): Antigravity Headless Runtime

A second session runtime is supported: `TEAM_GATEWAY_RUNTIME=antigravity` runs tenant turns through the Antigravity CLI (`agy -p <message> --output-format stream-json --print-timeout <N>s`), normalizing its NDJSON events (`init` / `step_update` / `result`) into the shared event shape — wire surfaces, quota accounting, and registry are runtime-agnostic. Continuity is explicit: turn 1's `conversation_id` is persisted on the tenant record and later turns pass `--conversation <id>` (no MRU lookups — the same determinism principle as the hermes named threads). Constraints: container isolation (`TEAM_GATEWAY_ISOLATION=docker`) requires the hermes runtime (the runtime image carries hermes, not agy) and the combination fails fast at startup; toolset scoping (`-t`) is hermes-specific and ignored on the antigravity runtime. Also landed in the same wave: T-20260927-019 fixed — pinned variant detection (`--version`) works again (`git ls-tree` instead of the invalid `git archive --list`), live-verified by a pinned gateway scaffold (template-v0.7.0).

## Addendum 4 (2026-09-27): Shared Credential Store (Replaces Per-Tenant auth.json Copies)

A user-reported silent test failure traced to credential death: seeding each tenant `HERMES_HOME` with a COPY of the operator's `auth.json` breaks as soon as any home refreshes the Nous Portal token — refresh tokens are single-use, so the copy goes stale, and every subsequent turn fails with provider-resolution errors while the gateway mechanics stay green. Fix: tenants no longer receive `auth.json` copies; every hermes spawn sets `HERMES_SHARED_AUTH_DIR` (Hermes' native cross-home token store, `hermes_cli/auth_nous.py` — "written on login AND every runtime refresh so the refresh_token stays current") to ONE shared dir, default `<seed>/shared`, configurable via `TEAM_GATEWAY_HERMES_AUTH_DIR`. This amends the seeding behavior in Decision 6 (`.env` is still copied; `auth.json` is not). Recovery note: tokens already invalidated require one interactive `hermes login`.

## Addendum 5 (2026-09-27): co-workspace Rebrand, Accounts with Email Verification, Admin Analytics

Three decisions land together:

1. **Rebrand + port**: the service is renamed **co-workspace** (UI, health payload, compose project/image names, service directory `services/co-workspace/`) and the default port is **9030**. Image names follow (`co-workspace-gateway`, `co-workspace-runtime`).
2. **PII-safe accounts (amends Wave B1)**: signup collects a **login ID + email + password**; the account stays pending until a verification key from the generated mail is entered. Privacy by data minimization — the raw email lives ONLY in the transient `pending_verifications` row (24h, deleted on verification); the users table keeps `email_hash` (SHA-256) for duplicate detection and never the raw email; login is by ID + password; the admin user list shows login IDs, never emails. The verification "mail" is generated to `<dataDir>/mail-outbox/` (dev/ops channel; a real SMTP integration is operator-side).
3. **Admin analytics**: `GET /admin/stats` — active/deleted users, tenants by status, total turns + tokens, total and per-principal disk usage (recursive dir size over tenant project + hermes home), tenants-per-variant, and a per-user rollup (tenant count, disk bytes, turns) for graphs. The demo page renders stat cards + horizontal bar charts and a user-management table (reset password → one-time token, delete with `archive|delete` disposition).

Also in this wave: the artifacts right panel (Files/Preview/History) with the tenant-confined files API and per-turn `turns` persistence, collapsible side panels, dark/light theme, sidebar sessions grouped by variant, and Claude Code + Codex CLI runtime adapters (provider disclosure in the models payload). Docker note: a stale container from the pre-rename project kept serving the old port alongside the new deployment — operators must `docker compose -p <old-name> down` (or remove the old container) after the rename.

**SEC-07 partial amendment (same addendum)**: the compose deployment no longer mounts the operator's full Hermes home — only `auth.json` + `.env` (ro, consumed by the per-turn re-seed) and the RW `shared/` token store. The gateway container can no longer read the operator's config.yaml or other provider credentials. The full least-privilege token broker (per-tenant credentials) remains upstream-dependent.

**Login-gate amendment (same addendum)**: `TEAM_GATEWAY_LOGIN_REQUIRED=true` makes the web UI session-gated (redirect to `/login`; local signup with email-verification key, Google SSO button when configured) while the API remains Bearer-key gated — a signed-in session cookie is ALSO accepted as an API credential so the demo page and scripts can share one identity. Login page: `/login`.

**Storage layout amendment (same addendum)**: tenant workspaces live under `<DATA_DIR>/storage/<principal>/<projectName>/{project,hermes-home}` — per-user grouping on disk (user request) instead of a flat `tenants/<id>` dir. The scaffold still executes in the workspace clone's `Projects/` (engine constraint) and relocates immediately; legacy `tenants/` paths keep working via per-record absolute paths.

## Addendum 6 (2026-09-28) — usability wave, account hardening, docker isolation deployment

User-approved wave (design: `docs/designs/2026-09-28-co-workspace-usability-wave-design.md`; meeting: `memory/meeting-2026-09-28-co-workspace-improvements.md`; PRs #1164–#1185):

- **Tenant-identity invariant (normative)**: one active team per (principal, variant), registry key `<variant>::<principal>`. `POST /sessions` is keyed and idempotent (`202` create / `200 existing`); the web surface never auto-creates (composer targets `POST /tenants/:id/chat`); the API wires keep lazy provisioning as their contract. Fixed en route: `?mine=1` now resolves the session-cookie principal, and `/sessions` stamps the registry key (created-vs-lazy divergence closed).
- **Accounts**: admin reset issues a one-time **temp password** (15 min, target sessions purged, forced first-login rotation) — the dead one-time-token flow is retired; self-service password change requires the current credential; self-service email change is verification-based and keeps hash-only storage; admins rename users but never read emails. Fixed: `/auth/*` is reachable without API keys (sign-in was impossible with keys configured); `createUser` stamps `login_id`/`verified_at`.
- **Web UX**: variant-grouped sidebar with persisted recency toggle; native chat streams live provisioning stages (SSE `: provisioning:` frames); New-team creation modal (beta toggle, typed message carried through creation); Enter sends / Shift+Enter newline (IME-safe); resizable sidebar/artifacts panels; `Cache-Control: no-cache` on HTML pages (browsers were running stale builds across redeploys).
- **Admin panel**: composition donuts (tenants by status / by variant / users by state; SVG, top-7+others), per-user ranking bars, users table with client-side search + paging; per-tenant disk sizing cached 60 s.
- **Docker isolation deployed**: the gateway image bakes the docker CLI and the compose mounts the host socket; per-turn siblings run as the hermes image's unprivileged user (10000) with SEC-10 caps and only the team's project + Hermes home mounted; the shared-auth store bind is skipped in docker mode (it flipped provider resolution → exit 111 — process mode keeps it); sibling host mounts derive from `CO_WORKSPACE_DATA_DIR_HOST` via `hostSidePath` (layout-agnostic).
- **Deployment posture**: single-tree deploys from the workspace checkout; compose `.env` (local-only) carries host paths — `CO_WORKSPACE_DATA_DIR_HOST` points at a durable `Storage/` bind, `/workspace` is the checkout itself.

## Addendum 7 (2026-09-29): Seed Home Directory Bind (amends the SEC-07 partial amendment)

The Addendum 5 SEC-07 narrowing mounted the seed credentials as **single files** (`auth.json`, `.env` → `/seed/...:ro`). Single-file binds pin the host inode: whenever Hermes refreshed its credentials on the host (observed 2026-09-29 08:50), the container kept reading the detached inode (zero bytes) and every turn failed with `ENOENT ... copyfile '/seed/auth.json'` on the per-turn re-seed — reported by the operator as "sending a question produces no response". The compose deployment now mounts the seed home as a **directory bind** (`${CO_WORKSPACE_HERMES_SEED_HOME}:/seed-home:ro`, service env `CO_WORKSPACE_HERMES_SEED_HOME=/seed-home`) and keeps `/seed/shared` as the RW store. Trade-off, accepted for the local single-operator deployment: the whole Hermes home (config.yaml, other provider credentials) is container-visible read-only; the server still reads only `auth.json` + `.env` from it. The same incident surfaced a second deployment gap: docker-isolation turns require the `CO_WORKSPACE_RUNTIME_IMAGE` (default `co-workspace-runtime:latest`) to exist on the host — the gateway image itself qualifies (it carries hermes), and a missing image failed every turn at spawn.

## Addendum 8 (2026-09-29): Provider Key + Base-URL Mode (amends the credential mechanism)

The copy-based OAuth credential flow is replaced by **static provider credentials**. Driver: Nous Portal revoked the operator's session (refresh-token reuse, `invalid_grant` 2026-09-29) — every Hermes instance holding a copy of `auth.json` is an independent refresher of the same single-use refresh token, so the per-turn re-seed architecture violated the OAuth rotation contract structurally. With `CO_WORKSPACE_LLM_BASE_URL` + `CO_WORKSPACE_LLM_API_KEY` set, isolated turns inject the key as `OPENAI_API_KEY`, the tenant config.yaml stamps `model.provider: custom` + `model.base_url` (re-stamped every turn, so existing tenants migrate without re-provisioning; the trust list also gains the isolated `/work/project` path), and the auth.json re-seed is skipped. Unset = the legacy shared-store path keeps working. Design: `docs/designs/2026-09-29-co-workspace-provider-key-config-design.md`. The provider **selector** mirrors the co-newbiz scheme (`CO_WORKSPACE_LLM_PROVIDER`: `openai | anthropic | gemini | custom`; default `custom`, `none` = off) and resolves the key's env name per provider (`OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `GOOGLE_API_KEY`).

## Addendum 9 (2026-09-29): Provider Key Stored in Tenant config.yaml (accepted risk)

Context: in provider key+base-url mode (Addendum 8) the gateway stamps `model.api_key` in plaintext into each tenant's `<hermesHome>/config.yaml` on every turn, in addition to injecting the key as an env var. The stamp is required: live-verified 2026-09-29 that hermes agent turns resolve the provider key via the profile secret scope and do not borrow ambient env (env-only turns 401'd). Trade-off: under docker isolation the tenant hermes home is mounted read-write into the turn container, so the agent's own tools can read the key, and a prompt-injected turn could exfiltrate it because network egress is open. The per-tenant files API is rooted at the project directory only and does not serve the hermes home. The AGENTS.md invariant that secrets never appear in API responses or logs remains true.

Accepted risk: single-operator deployment. The operator should use a dedicated, scoped, low-limit provider key and rotate it on suspicion. Mitigations that ship with this change (T-20260929-006): YAML-safe quoting of stamped values, restrictive file mode where possible, and passing the key to docker as `-e NAME` so no value appears on argv. Review: `docs/reports/2026-09-29-project-review-co-workspace.md`.

## Addendum 10 (2026-09-29): Provider Selector Corrections (amends Addendum 8)

Addendum 8 and design R2/R6 under-described the shipped provider mode. Verified against `services/co-workspace/src/config.ts`, `tenant.ts` and `server.ts`:

- **Providers**: `CO_WORKSPACE_LLM_PROVIDER` accepts `openai | anthropic | gemini | zai | custom` (default `custom` when a key is set; `none` = off). `zai` is first-class (hermes's `zai` provider; pairs with `https://api.z.ai/api/anthropic`).
- **Key env name is per provider**, not always `OPENAI_API_KEY`: `openai`/`custom`/any other name -> `OPENAI_API_KEY`, `anthropic` -> `ANTHROPIC_API_KEY`, `gemini` -> `GOOGLE_API_KEY` (an exact-name entry in hermes's env allowlist; the `GOOGLE_` prefix is not allowlisted because `GOOGLE_CLIENT_SECRET` is a gateway secret), `zai` -> `ZAI_API_KEY`.
- **`model.provider` mirrors the selector value** (lower-cased), so the stamp is `custom` only when the selector is `custom` or unset; it is not always `custom` as Addendum 8 states. `model.base_url` is stamped from `CO_WORKSPACE_LLM_BASE_URL` (required for `custom`, an optional override for named providers).
- **Reasoning effort**: `CO_WORKSPACE_HERMES_REASONING_EFFORT` stamps `agent.reasoning_effort` into each tenant config so thinking-mandatory models (e.g. glm-5.3-flash) accept requests. In key mode an unset variable resolves to `low`; an explicitly empty value omits the stamp (the compose file uses `${VAR-low}` without a colon so an empty host value reaches the server as empty).
- **Gemini env name** in Addendum 8 and the design (`GOOGLE_API_KEY`) is unchanged and correct; the design's earlier claim that the allowlist passes the whole `GOOGLE_` prefix is withdrawn.
- **Compose socket note (amends Addendum 6)**: the base compose no longer mounts the Docker socket; `CO_WORKSPACE_ISOLATION=docker` requires also including `docker/docker-compose.isolation.yml`.

## Addendum 11 (2026-09-30): Non-root gateway, docker socket proxy, optional seed home

**Context**: findings C3 and M6 and ticket T-20260929-014 of `docs/reports/2026-09-29-project-review-co-workspace.md`. Addendum 10 moved the raw `docker.sock` mount into the opt-in `docker-compose.isolation.yml`; the gateway still ran as root with the socket (host-root equivalent) and always mounted the whole Hermes seed home (Addendum 7).

**Decision**:
- The gateway container runs as `10000:10000` (`CO_WORKSPACE_GATEWAY_UID/GID` override) with `no-new-privileges` and all capabilities dropped. This is the same uid as the sibling turn containers (`--user 10000:10000`), so files it creates are already owned by the turn user. `chownTree` in `src/tenant.ts` is a no-op unless the process is root.
- Docker isolation no longer mounts the socket into the gateway. A `tecnativa/docker-socket-proxy` service holds it read-only on an internal-only network; the gateway uses `DOCKER_HOST=tcp://docker-proxy:2375` (passed through by `dockerCliEnv`). Enabled groups: containers, POST, DELETE, start/stop/restarts. Disabled: exec, images, volumes, networks, info, build, swarm, secrets, system, plugins, auth, commit.
- The Hermes seed home mount moved to the optional `docker-compose.seed.yml` (legacy OAuth mode only).

**Consequences**:
1. Residual risk (honest): the proxy filters by API endpoint only and cannot inspect the container-create body. A compromised gateway can still request a privileged container or a bind mount of `/`. Host-root equivalence is reduced, not removed. Follow-ups: rootless Docker or a create-body-validating broker.
2. Operational changes for existing deployments:
   - On Linux, chown the data dir and the shared auth dir to 10000 once (macOS Docker Desktop maps ownership). The workspace clone must be writable by uid 10000.
   - Docker isolation now starts a proxy container, so its image must be pulled at `docker compose up`. It needs the pre-built runtime image: with `IMAGES=0` a missing image fails fast instead of pulling.
   - With a `COMPOSE_FILE` from before this change, the seed home is no longer mounted. Operators of legacy OAuth mode, or relying on the seed `.env` copied into tenant homes, must add `docker-compose.seed.yml`.
   - The `.env.keys` and shared-store host defaults still fall back to `CO_WORKSPACE_HERMES_SEED_HOME` when set, otherwise to `<data dir>/seed`.

**Live verification (2026-09-30)**: Docker 29.8.1 on macOS Docker Desktop, using an isolated compose project and image tag with dummy provider values and no real provider. The operator's running deployment was not touched.
- Image tags exist and pull: `tecnativa/docker-socket-proxy:0.3.0` (30 MB), `oven/bun:1.4`, `docker:cli`, `nousresearch/hermes-agent:latest`. The gateway image builds with the new Dockerfile (`--frozen-lockfile --production`, `USER 10000:10000`).
- The Hermes base image already has a `hermes` user with uid/gid 10000 (home `/opt/data`). As uid 10000 the gateway image runs bun 1.4.2, git 2.47.3 and docker CLI 29.8.1, and `HOME=/home/gw` is writable.
- **Finding (bug fixed in this change)**: the proxy image crash-loops with `read_only: true`, because its entrypoint renders `/usr/local/etc/haproxy/haproxy.cfg` from `haproxy.cfg.template` in the same directory at start (a tmpfs over that directory would hide the template). The override now leaves the proxy root filesystem writable; a unit test guards this.
- With the fixed override the gateway starts as uid 10000, logs `docker isolation: server 29.8.1` (the startup probe through the proxy with `INFO=0` works: `HEAD /_ping`, `GET /version`), and the boot reaper runs (`orphan turn reap: found 0, removed 0`).
- Through the proxy, from inside the gateway, `docker image ls`, `volume ls`, `network ls`, `exec` and `info` (server part) return 403 Forbidden, and `/var/run/docker.sock` does not exist in the gateway.
- Team create (`POST /sessions`, provisioning as uid 10000 into the mounted data dir and workspace clone) reached `ready` in about 6 s. A chat turn created the sibling turn container through the proxy (create/attach/start/wait) with the expected `--name` and `co-workspace.turn/tenant/instance` labels. `POST /tenants/:id/cancel` returned `cancelled: true` in 6 ms and the container was gone within 1 s (kill through the proxy, `ALLOW_RESTARTS`); the SSE stream ended with exitCode 137. `DELETE /tenants/:id` removed the tenant folder with no permission errors. After a gateway restart the boot reaper reported `found 1, removed 1` for a labeled orphan and left an other-instance container and an unlabeled decoy alone (`ps` + `rm -f` through the proxy, `DELETE=1`).
- **Residual risk, confirmed concretely**: with `CONTAINERS=1` the gateway can list every container on the daemon, including other projects' containers, with `docker ps -a`, and `docker inspect` returns a container's environment variables (the test printed only variable names of the proxy's own container; no other container's values were read). Reading container logs belongs to the same endpoint group but was not tested. The proxy still cannot inspect the create body (privileged / bind-mount of `/` remain possible). Guidance: do not run other sensitive workloads on the same Docker daemon as the gateway. Follow-up: rootless Docker or a broker exposing only run/list/kill for its own labeled containers.

**Still unverified**: a real provider chat turn end to end (the turn container started, but the model endpoint was an unreachable dummy); Linux host bind-mount ownership behavior (verification ran on macOS Docker Desktop); Google SSO; legacy OAuth mode with the seed override.

## Addendum 12 (2026-09-30): co-workspace is not registered in services.yaml

**Context**: finding M20 of `docs/reports/2026-09-29-project-review-co-workspace.md` noted that co-workspace is absent from `services.yaml` and that the ADR's workspace-schema allowlist claim could not be found. Verified: `services.yaml` is the ticket-runner catalog (`schemaVersion: 1`; each entry has `id`, `name`, `description` and a `run` of type `script` or `skill`). It is read by `bun scripts/ticket.ts create <service-id>` (service tickets), which fails with `unknown service id` for anything not listed. It is a catalog of run-to-completion jobs and currently holds only `audit`. co-workspace is a long-running HTTP server deployed with docker compose (`services/co-workspace/docker`), which does not fit a `script|skill` entry. The second claim of the finding was not accurate: the top-level `services` directory is in `rootAllowlist.dirs` of `docs/workspace-schema.json`. The allowlist covers that directory, not per-service names (Decision 1 wording corrected accordingly).

**Decision**: do not register co-workspace in `services.yaml`. Its deployment and operation are documented in `services/co-workspace/README.md` and this ADR.

**Consequences**: if a run-to-completion maintenance job for co-workspace is needed later (for example a health probe or a data-dir audit), register that job as its own `script` entry rather than registering the server.

## Addendum 13 (2026-09-30): Docker broker rewritten as a raw socket proxy (amends Addendum 11)

**Context**: PR #1253 (T-20260930-008) replaced the tecnativa socket proxy with a create-body-validating broker. The adversarial review in `docs/reports/2026-09-30-co-workspace-docker-broker-security-review.md` (PR #1257) found it both bypassable and unusable. It validated a parsed copy but forwarded the raw text, and Go's daemon decodes keys case-insensitively with the last duplicate winning. `CapAdd` was unchecked, `SecurityOpt` only had to contain `no-new-privileges`, and `User` was checked under `HostConfig` although it is a top-level create field. Only unversioned paths and `GET /_ping` were allowed, while the CLI sends `/v1.56/...` and `HEAD /_ping`. Bind sources were only prefix-checked. Measured with Docker CLI 29.8.1: a fetch-based proxy cannot carry `docker run -i` (attach is an HTTP upgrade; stdin and output were lost while the CLI still exited 0), and the CLI addresses the container by 64-hex ID after create, so name-prefix scoping rejected everything after create.

**Decision** (T-20260930-027; design `docs/designs/2026-09-30-coworkspace-docker-broker-raw-proxy-design.md`): `src/docker-broker.ts` is now a raw socket proxy and `src/docker-broker-policy.ts` holds the pure policy. One request per connection with strict head parsing; the upstream head is rebuilt from scratch; the create body is forwarded as the canonical re-serialized text only; attach is a bidirectional pipe with upstream half-close; pipelined bytes close the connection. The policy uses a strict JSON scanner, an exact allowlist of every key at every level, exact values for `User`, `CapDrop`, `SecurityOpt`, image, entrypoint, env, labels and binds, and resource caps from the gateway's env. Container refs are resolved through an internal inspect and forwarded as the full ID only for turn-pattern names carrying this instance's label. Bind sources are `lstat`-walked at create and re-checked at start (the broker mounts the data dir read-only at the same host path). Inspect and resize are removed from the allowlist.

**Consequences**:
1. Addendum 11's residual-risk list is replaced: a compromised gateway can still create, start and kill the turn containers it owns within the policy bounds, and the turn containers' environments are no longer readable through the broker.
2. The symlink race between the start-time check and the daemon resolving the bind source cannot be closed by any string or `lstat` check while the gateway can write the data dir. The broker narrows it to milliseconds. Rootless Docker or userns-remap is the only complete fix and remains the long-term direction.
3. The broker still runs as root (socket access), with all capabilities dropped and a read-only rootfs.

**Verification (2026-09-30)**: 136 unit and integration tests across `co-workspace-docker-broker-policy.test.ts` and `co-workspace-docker-broker.test.ts`, including a replay of a real CLI capture through a fake daemon; removing the raw-vs-canonical rebuild, the start re-check, the create-time walk, the pipelining close, `Transfer-Encoding` rejection, the duplicate-key scan or the `User` check each fails a test. Live on Docker 29.8.1 (macOS Docker Desktop, isolated compose project, dummy provider values): startup probe, boot reaper, team create, one chat turn with the real CLI (create, attach, wait, start; `system init` received), cancel, delete and orphan reaping (including a short-ID delete) all work through the broker; 24 attack requests from inside the gateway were all refused with a specific reason and created nothing (case-variant and duplicate keys, `CapAdd`, `User 0:0`, unconfined seccomp/apparmor, `..` and `/etc` binds, a symlink planted at create time, a symlink swapped in before start, `VolumesFrom`, `PidMode container:`, host network, foreign image, forged label, inspect, kill/delete of the gateway and broker, `%2F` traversal, exec, images/volumes/info).

**Unverified**: Docker Desktop versus Linux symlink semantics on real bind mounts; backpressure under very large output; a real provider turn end to end; Linux data-dir ownership with the read-only broker mount.

## Addendum 14 (2026-09-30): opt-in volume-subpath mode closes the bind-source symlink race (T-20260930-038)

Setting `CO_WORKSPACE_DATA_VOLUME` to a Docker volume name switches tenant storage from host binds (`HostConfig.Binds` plus the broker's lstat walk) to daemon-side volume-subpath mounts (`HostConfig.Mounts` with `VolumeOptions.Subpath`). Because the subpath is resolved by the daemon from the volume root and can never name a host path, the F3 bind-source symlink TOCTOU is closed by construction in this mode: live on dockerd 29.8.1, a symlink planted inside the volume at the mounted subpath is rejected at mount time with "path concatenation escapes the base directory" instead of being followed. The default bind mode is unchanged, and its accepted milliseconds-wide check-to-mount race remains documented residual risk; rootless Docker or userns-remap stays the only complete daemon-level fix for the remaining trust assumptions.

## Addendum 15 (2026-09-30): API keys and the login-required web UI are composable

**Context**: enabling API keys (`authEnabled: true`) alongside `CO_WORKSPACE_LOGIN_REQUIRED=true` — the posture any non-loopback deployment needs — broke both surfaces (found live 2026-09-30 while enabling LAN access). First, `GET /login` was not in `AUTH_EXEMPT_ROUTES`, and a fresh browser holds neither a key nor a session, so the sign-in flow (`GET /` → 302 → `GET /login`) dead-ended in 401. Second, the Wave B gate demanded a session from every non-exempt caller when login was required, including callers presenting a valid Bearer key — key-authenticated `GET /v1/models` / `GET /tenants` were redirected to `/login` (302) and mutating routes returned 401 "sign-in required", contradicting the gate's own contract ("the API demands a key or a valid session") and breaking every API wire.

**Decision** (design `docs/designs/2026-09-30-coworkspace-login-exempt-design.md`): `GET /login` joins `AUTH_EXEMPT_ROUTES` (static shell content, no tenant data; `POST /auth/login` stays on the always-open, rate-limited `/auth/*` surface), and the Wave B session demand exempts key-authenticated callers via the already-computed `hasApiKey` — no new credential handling. Additionally, the compose publish binding is env-driven (`${CO_WORKSPACE_PUBLISH:-127.0.0.1}:9030`) so deployments keep the D6 loopback default while a LAN/all-interface exposure is one `.env` line instead of a compose edit.

**Resulting matrix** (`loginRequired=true`, keys configured): sign-in page 200 keyless; web shell `GET /` 302s keyless and serves with a session; tenant/model API routes 401 keyless (route gate runs first), 200 with a key or a session; unauthenticated mutating routes 401. Keyless mode (empty key pool) is unchanged.

**Verification (2026-09-30)**: 416 unit/integration tests pass (`co-workspace-phase2` route-gate pin for `GET /login`; `co-workspace-auth-hardening` handleRequest-level Wave B cases: login page reachable keyless with keys on, key-authenticated `GET /tenants` 200 without a session, unauthenticated web shell 302 + tenant API 401). Live on the LAN deployment: same matrix verified over `http://<lan-ip>:9030/` with a real key file, including `POST /auth/login` reaching its credential check.
