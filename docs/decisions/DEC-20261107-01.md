## Decision context

The workspace user ruled on 2026-11-07 that `Projects/co-abap-plugin` is a
separate project, not a member of the template fleet: it is a Claude Code
plugin distribution (`plugin.json` + `commands/`), it has no
`variant.json`, and its last template sync (2026-10-03, template 0.10.0)
is historical residue rather than an open obligation. Operations did not
match the ruling: there was no machine-readable fleet-membership record,
and ~20 scripts independently discovered fleet members by enumerating
`Projects/co-*`, so every fleet automation surface — the 01:30 runner,
resync/audit tooling, fleet analytics, and template-drift checks — treated
`co-abap-plugin` as a member. Left as-is, the next resync window, upgrade
wave, or learning-extraction run would re-impose template obligations the
user explicitly removed. This record fixes the disposition so the
implementing specialist executes against a settled contract; the design
doc carries the consumer inventory (§3), the registry schema and failure
semantics (§4), the helper API (§5), the exclusion semantics per surface
(§6), and the runner-prompt wording (§7). Status `accepted` records the
gate-moment adoption; the implementation PR lands after user approval of
the design — the registry file and code paths registered by this decision
ship in that PR.

## Conditions attached

1. `scripts/lib/fleet.ts` is the sole membership-derivation path: no
   script outside it may filter a `Projects/` readdir by the `co-` prefix,
   enforced mechanically by tests/unit/fleet-iteration-routing.test.ts
   (design §9.3, two-layer guard).
2. The registry is L0-only: never added to any propagation map, the
   common-contract delivery, or L1/L2 deliveries; the structural guard
   treats any `templates/common` appearance of the fleet helper as a
   failure (design §11).
3. A malformed registry hard-fails fleet tooling; the runner never falls
   back to a raw `Projects/co-*` glob, even as a fallback when the helper
   fails (design §7).
4. The PM applies the §7 wording to the live 01:30 runner prompt (outside
   the repo) in the same window the implementation PR lands; until then
   the design doc §7 wording is the record.
5. R43 ("Derive the variant set with the glob `templates/co-*`") stays
   verbatim — template variants and fleet members are deliberately
   different sets (design §7).
6. Reversal path: remove the exclusion row from the registry — the record
   is the reversal path; no code change either way.
7. Delivery exception, recorded at implementation (IC-01 collision): three
   of the routed A-sites (A3 evidence-backport-scan, A6 audit
   checkProjectDocMarkerDrift, A8 validate-templates
   checkProjectIdentityPlaceholders) live in L0+L1-delivered scripts, so
   the l1-import-closure gate (validate-templates IC-01, spec
   2026-10-26-project-review-remediation-design D4) forces the leaf
   pure-module helper scripts/lib/fleet.ts into the delivered closure per
   its own fix policy (ADR-0073 Amendment 4). The design §11 "never
   delivered" rule is amended FOR THE HELPER ONLY: the registry
   docs/fleet-membership.json stays strictly L0-only (never propagated,
   never in any delivery list — verified against the propagation map and
   the delivery contract), fleet-list.ts stays L0-only, and a delivered
   helper copy reads the PROJECT's own docs/fleet-membership.json (absent
   in every project → zero exclusions → historical behavior), so no
   workspace membership state ever reaches L1/L2. Pinned by
   tests/unit/fleet-iteration-routing.test.ts (delivery-deviation pin).
