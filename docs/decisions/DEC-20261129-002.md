## Context

On 2026-11-29 the automation-engineer and architect produced the manual
ticket description design (docs/designs/2026-11-29-ticket-manual-description-design.md)
after the day's evidence: T-20261124-014 carried a full multi-sentence
disclosure inside its `title:` folded block, T-20261129-001 had to be filed
through the service path purely to obtain a description surface, and the
defect's own ticket (T-20261129-013) had to compress its whole rationale
into its title. The design carried three open questions (§10 Q1-Q3) and
`Status: draft (pending Row 0 owner approval)`.

Evidence. The owner reviewed the design and confirmed approval on
2026-11-29, adopting Q1-Q3 to the design's recommended options and ruling
that implementation follows immediately in the same train — the approval
PR and the implementation PR land back to back, unlike DEC-20261129-001's
approval-now/implement-later split. The approval is the owner's only act
recorded here; both landings are executed by the automation-engineer at the
PM's dispatch.

## Decision

The approval in the frontmatter is recorded as the ruling.

Scope limits. This decision does NOT approve:

- Any change to service tickets' `inputs.description` convention (its
  consumers exist; the working surface is not churned).
- Any migration of already title-stuffed tickets (T-20261124-014 remains a
  valid record; repair into title + description is an optional human
  hand-edit).
- Any new upstream-block field, MCP server change
  (`scripts/mcp-upstream-server.ts`), or kind conversion.
- `list` rendering changes (§8 out of scope).

The approval landing set is exactly: the design doc (header `Status`
amended to approved, one dated 2026-11-29 amendment line, content otherwise
verbatim), the spec-registry entry `2026-11-29-ticket-manual-description-design`
flipped `draft` → `approved`, `docs/specs/registry.json` (regenerated
projection), this decision record, and the pipeline bookkeeping (memory log,
VERSION_MANIFEST, CHANGELOG entry). The implementation lands in the
immediately following PR, which flips the spec entry to `implemented`.

## Consequences

- The design is tracked, registered, and auditable before its code lands;
  the implementation PR's spec-check references this entry.
- T-20261129-013 closes through the implementation train (move to review,
  then done) after the implementation PR merges.
- The Q1-Q3 rulings bind the implementation: a 2000-char cap named in the
  validation error, show-only rendering, and no description-vs-upstream
  invariant are fixed terms of the delivery.
- Existing tickets without the field stay valid (additive-optional, the
  v1.10.0 `sev`/v1.11.0 `hub` tolerance precedent); no schema-version
  migration.
- No template propagation and no variant delivery: the whole surface is
  L0-only per AGENTS.md §3.7.5.
