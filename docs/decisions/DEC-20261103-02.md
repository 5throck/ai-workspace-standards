## Decision context

The nightly scaffold E2E (run 41409778763) has been red since 2026-11-02:
`checkHubDoctrineDuplication` (scripts/helpers/hub-topology.ts:566-600) FAILs
any local copy of a foreign hub-doctrine asset that is neither a declared
consumer copy nor common-contract stock, and it does not yet honor
variant-identity registry rows as a sanction. Batch E5/E6 (co-architect
template promotion) registered co-architect's CAD skills as variant-identity
but missed the hub-doctrine reconciliation for agents/architect.md, which
shares its rel-path with co-develop's registered hub-doctrine architect agent
while carrying an entirely different role brief. The ticket offers two
dispositions — variant-identity registration (preferred) or declaring
co-develop consumption — and this record adopts the preferred one so the
implementation change set executes a decided rule.

## Conditions attached

1. The registry row lands together with the §15.1 checker sanction — the row
   alone does not unblock scaffolds, and the sanction alone (without the row)
   would leave co-architect failing.
2. Both schema copies change in the same commit; the hash-parity gate
   (validate-templates.ts:1240-1257) is the enforcement.
3. variant.json hub.consumes for co-architect is explicitly unchanged; any
   future co-develop consumption requires a new gate-moment record.
