## Ruling

1. **Design Gate**: the change touches the registry SSOT
   (`docs/workspace-schema.json` `models`), the validator
   (`PLATFORMS` const, v1.4.1 → v1.5.0), `AGENTS.md` §3.6 prose, and 9 agent
   frontmatter blocks. It is a multi-surface logic and schema change, so no
   exemption code applies. Design doc:
   `docs/designs/2026-10-23-zai-tier-floor-support-design.md`
   (spec `2026-10-23-zai-tier-floor-support`, new — no existing registry entry).
2. **Approval with scope amendment (2026-10-23)**. The user approved full
   registration and extended it — verbatim:

   > "hermes와 Z.AI 모두 레지스트리에 등록된 후 검증 스크립트에도 포함될 수
   > 있도록 해줘"

   Translation: "Make sure both hermes and Z.AI end up registered in the
   registry and then covered by the validation script as well."

   Effect on the proposed design: D3 becomes full registration for BOTH
   platforms — `PLATFORMS` grows from 5 to 7 entries (`claude`, `gemini`,
   `antigravity`, `gemini-cli`, `codex`, `hermes`, `zai`). D4 becomes: all 9
   `agents/*.md` frontmatter blocks gain BOTH a `hermes:` line and a `zai:`
   line; each agent's hermes tier mirrors its existing claude tier (the
   registry maps hermes → claude ids, e.g. architect
   `hermes: high  # claude-opus-5-5`, pm `hermes: medium  # claude-sonnet-5-5`);
   zai comments follow the approved mapping (`# glm-5.3` on high,
   `# glm-5.3-flash` on medium/low). The validator then actively checks both
   new platforms.
3. **Platform key**: `zai` — approved as proposed. The existing keys name
   tools, so this deviates from convention by design:
   services/co-workspace already resolves provider id `zai` (`ZAI_API_KEY`,
   lowercase ids `glm-5.3` / `glm-5.3-flash`), and the models are reachable
   through two paths (ZCode host, direct API). A provider-level key covers
   both; a tool-level key (`zcode`) would not.
4. **Tier mapping**: high=glm-5.3, medium=glm-5.3-flash, low=glm-5.3-flash —
   approved as proposed (the gemini flash pattern). A PM session on
   GLM-5.3-Flash sits at the medium floor instead of below it. Reasoning
   levels (low/high/max, default max) are documented in the §3.6 note block,
   together with one tight sentence noting that hermes validates against the
   claude column model ids.
5. **Hermes distinct-id note**: `models.hermes` mirrors `models.claude`, so
   the §3.6 "distinct" deduped union gains ONLY the GLM column (`glm-5.3` on
   high, `glm-5.3-flash` on medium and low); hermes contributes no new ids.
   No `HERMES.md` prose target is created — the CLAUDE.md target already
   validates the claude ids, and hermes-specific drift is covered by
   `PLATFORMS` membership and frontmatter checks. The former "hermes
   PLATFORMS gap" follow-up is resolved in-scope and removed.
6. **Delivery**: root PR (schema zai block, validator PLATFORMS 5→7 + v1.5.0,
   §3.6 both managed blocks, governance note copy, 9 agent files ×2 new
   lines) then template PR (template twins + managed blocks in all 14
   `templates/co-*/AGENTS.md` + parity-test glm assertions). The template PR
   touches more than 3 template files and stays flagged high-risk; the ruling
   itself constitutes the user confirmation for proceeding. The constitution
   §5.6 tier table (already stale — it omits codex) stays left-and-flagged
   for a docs-writer refresh; the §5.6 line ~32 example frontmatter gains
   codex, hermes, and zai lines in that same follow-up.

## ADR assessment

No ADR required. The change extends an existing registry under semantics
already fixed by the 2026-09-29 tier-floor design; hermes registration reuses
the claude id namespace, so no new model-id taxonomy or gate semantics is
introduced. Reassess if ZCode gains model-passing dispatch (enforcement
semantics change, design follow-up E), or if hermes ships its own model ids
(would need a HERMES.md prose target and a §3.6 distinct-set review).

## Consequences

- ZCode sessions get a declared tier floor: PM on GLM-5.3-Flash is at-floor
  (silent); agent dispatch mapping is declared per tier.
- hermes closes its registry gap: promoted from schema-only to a fully
  validated platform alongside zai; the pre-ruling inconsistency disappears.
- The validator checks both new platforms in frontmatter and (for zai) in
  §3.6 prose; drift on either side fails
  `bun scripts/validate-model-registry.ts`.
- The §3.6 tier lines grow from 3 to 4 models per tier (GLM column only);
  the managed-block-parity test keeps its old assertions green through both
  PRs and gains glm assertions in the template PR.
- Template-PR cost is real: 14 variant `AGENTS.md` files must take the two
  managed-block updates byte-identically (managed-block parity), and all
  agent frontmatter twins gain two lines each.
- ZCode tier enforcement remains declarative until the `.zcode/agents`
  follow-up or a ZCode model gate lands.
