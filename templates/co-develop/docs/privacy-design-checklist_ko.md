# 개인정보보호 설계 체크리스트 — 개인데이터 컨설팅 산출물

*privacy-design-checklist_ko.md version: 1.0 — 영문판과 함께 갱신 (2026-09-06)
<!-- privacy-design-checklist.md (EN)의 한국어판입니다. 두 파일은 함께 갱신합니다. -->

위협 모델 한 줄 요약: **유출된 데이터베이스는 아무것도 노출하지 않아야 하고,
관리자는 특정 개인의 결과를 조회할 수 없어야 한다.**

## 설계 원칙 (체크리스트)

### 1. 저장 데이터 (Data at rest)

- [ ] 개인 필드(이름, 이메일, 회사, 부서, 주관식 답변 등)는 **저장 시 암호화**
      (예: AES-256-GCM 등 인증형 암호).
- [ ] 암호화 마스터 키는 **데이터베이스 외부**에 보관(환경변수 또는 제한적
      권한의 키 파일)하며, **데이터베이스와 함께 백업** — 키 분실 시 복구
      불가능함을 운영자에게 문서화.
- [ ] 조회가 필요한 필드(예: 이메일 로그인)는 **키드 해시(HMAC) 컬럼** 사용 —
      평금 저장 금지, 검색 가능한 암호문 금지.
- [ ] 비밀번호/시크릿은 **레코드별 솔트를 둔 느린 해시**(scrypt/argon2/bcrypt)
      로 저장하고 상수 시간 비교.

### 2. 식별정보 최소화

- [ ] 로그인 식별자는 필요한 **최소한의 지속 식별자**만 사용 (원 사례: 참가자
      이메일 — 나머지는 자격증명이 아닌 프로필 데이터).
- [ ] 하드코딩된 기본/초기 자격증명이 시스템 어디에도 존재하지 않음.
- [ ] 모든 특권 역할은 **대역 외(band-out) 승인 채널**로 부트스트랩 (예: 단일
      사용 이메일 코드, 짧은 TTL의 HMAC 저장) — 본인이 통제하는 채널로 신원
      고정.

### 3. 관리자 vs. 참가자 가시성

- [ ] **활성화와 관리의 분리**: 계정을 발급/초기화하는 주체가 평가 내용이나
      개인 결과를 볼 수 없음.
- [ ] 참가자는 관리자에게 **가명 코드**로 표시; 개인 식별자는 서버 밖으로
      노출되지 않음.
- [ ] 개인별 결과는 **관리자 열람 불가**; 집계에는 **k-익명성** 적용(소규모
      그룹 억제, k ≥ 5).
- [ ] 계정 관리를 위해 식별자를 노출해야 할 경우 **서버 측 마스킹**
      (예: `a***e@domain`) — 전체 값 렌더링 금지.

### 4. 자격증명 수명주기

- [ ] 관리자는 참가자 자격증명을 **초기화만 가능, 열람/지정 불가**.
- [ ] 임시 자격증명은 무작위 생성, **참가자 채널로 직접 전달**(이메일) —
      관리자 API를 경유하지 않음.
- [ ] 일회용 코드/자격증명은 짧은 TTL의 키드 해시로만 저장, 사용 후 무효화;
      초기화 시 **기존 세션 무효화**.
- [ ] 전달 채널 폴백(SMTP 미구성 시)은 문서화된 수동 절차 — API 응답으로
      노출하지 않음.

### 5. 무결성 & 검증

- [ ] 채점/집계는 **서버 측** 실행; 클라이언트가 제출한 모든 항목을 저장 전에
      재검증(항목 ID 존재, 값 범위).
- [ ] 민감한 값은 로그에 미출현; 로그 파일도 데이터베이스와 동일한 체크리스트로
      감사.

## 검토 절차

1. 이 체크리스트는 **설계 검토**(구현 시작 전), 보안 감사 pass, 클라이언트
   인도 전에 실행한다.
2. 미체크 항목에는 서면 근거 또는 후속 티켓이 필요 — 침묵은 승인이 아니다.
3. 개인 필드가 포함된 스키마 변경은 1항을 재발동한다 (`docs/co-develop.context.md`
   수명주기 표의 Zod/계약 gate 적용).
