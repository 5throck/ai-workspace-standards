# co-utility 프로젝트 사용 가이드

이 문서는 co-utility 프로젝트의 일상 운영 방식(요청 접수부터 PR 병합까지)을
설명합니다.

## 누가 무엇을 하나

모든 요청은 PM 게이트웨이를 통과합니다. PM이 요청을 분류하고 전문 에이전트를
디스패치하며 PR을 생성합니다. 사용자가 직접 에이전트를 고를 필요가 없습니다.

| 하려는 작업 | 진행 방식 |
|-------------|-----------|
| 기능 추가/변경 | PM이 `backend`(코어/API/CLI)와 `frontend`(UI)를 디스패치 |
| UI 언어 추가 | PM이 `i18n-specialist`를 디스패치해 로케일 매트릭스 변경 |
| 버그 보고 | PM이 분류하고, `qa`가 재현, 소유 전문가가 수정 |
| 의존성/입력 감사 | PM이 `security`를 디스패치해 스캔·보고 |

## 작업 루프

1. **요청** — 원하는 결과를 설명합니다. PM이 분류하고 실행 계획표를 작성해
   에이전트 실행 전에 보여줍니다.
2. **설계 게이트** — 실질적 변경은 코드 작업 전에 짧은 설계 노트를
   `docs/specs/`에 등록합니다. 사소한 변경은 면제 코드를 사용합니다.
3. **구현** — 전문가들이 직렬로 작성(backend → frontend → i18n)해 파일 잠금
   충돌을 피하고, 매 수정 후 post-write 품질 게이트를 실행합니다.
4. **검증** — `qa`가 전체 테스트를 실행하고, `security`가 새 외부 입력
   표면을 재감사합니다.
5. **동기화** — PM이 `/sync` 파이프라인을 실행합니다: 감사, 체인지로그,
   세션 로그, 브랜치, 커밋, 푸시, PR. 기본 브랜치 직접 푸시는 훅이 차단하며
   모든 변경은 검토 가능한 PR로 도착합니다.

## 다중 인터페이스 기본 규칙

동작 변경은 코어 서비스 모듈에 먼저 반영되고, 웹 UI·데스크톱 셸·CLI 어댑터가
그로부터 전파받습니다. 같은 로직이 두 인터페이스에 중복되어 있다면 결함입니다.
PM에게 서비스 계층 통합을 요청하세요.

## 로케일 변경

하나의 로케일 = 하나의 원자적 변경: JSON 파일, 런타임 로더 레지스트리, 언어
선택기, 테스트 기대값이 함께 움직입니다. 그렇지 않으면 패리티 감사가 의도대로
큰 소리로 실패합니다.

## 파일 위치

| 경로 | 내용 |
|------|------|
| `src/` | 애플리케이션 패키지 (코드 + 템플릿 + 정적 자산 + 로케일) |
| `tests/` | 테스트 스위트 — 모든 변경의 합격 기준 |
| `docs/` | 프로젝트 컨텍스트, 스펙, 거버넌스 기록 |
| `memory/` | 세션 로그(`YYYY-MM-DD.md`)와 `MEMORY.md` 인덱스 |
| `CHANGELOG.md` | 릴리즈별 사용자 대상 변경 내역 |
